# 按需交付意见

用户需要现场建议、检测委托要点或部门回复时读取本文件。可直接在聊天中给出草稿；明确要求文件时才 export。无需先保存咨询，不主动弹窗要求选择格式；按用户所说的用途判断，真正不清楚时再问。不得自行发送、盖章或宣称已审核。

在最新 answer.deliverables 中只写实际需要的类型，每个字段均为非空文本数组。未知和缺失应写明，不使用虚构单位、实测值、日期、检测结果或条文填空。共用当前 answer.summary、claims、limitations；规范判断仍须在 claims 中绑定合格审阅。交付正文应与这些依据一致，不在交付字段另塞未经核实的规范结论。

## field_advice：现场处置建议

- priority_actions：先做什么及目的，结合当前风险和暴露情况。
- pause_conditions：何种变化或未知条件下暂停现场作业、报告并交专业核查。不把暂未观察到变化写成安全许可。
- handoff：下一步找谁、携带什么已有资料、要解决什么问题。未落实的行动写“建议／待落实”，不能记成已执行。

默认按“先做什么—何时暂停—下一步找谁”排序；不替相关单位签发交通管制或恢复通行决定。

## inspection_brief：检测委托要点

- objective：需要解决的工程疑问，避免以已认定病因为前提委托。
- scope：设施、构件、部位及拟核查范围，界限未知时写明。
- available_materials：确实已有的资料、来源与缺失，不将建议调取资料列成已有。
- requested_work：拟请检测单位核定的调查项目，每项说明用途；方法与参数未经核定时保持待定。
- constraints：现场通行、进入条件、资料授权及实施前提；未知不视为已满足。
- expected_outputs：希望成果回答哪些问题、呈现何种定位／记录、保留哪些不确定性，以及怎样支持后续决策。

这是用于沟通委托需求的草稿，不冒充正式检测方案、合同、资质认定或已确定的检测数量。

## department_reply：部门回复草稿

- conditional_conclusion：先写在什么条件下可形成什么意见，以及当前能确认到哪一步。
- basis_and_gaps：事实来源、已核实依据和影响结论的证据缺口；无规范原文就说明未核实。
- verification_checklist：需补充核查的事项及其目的，无法确认的职责、期限不虚构。
- coordination：建议由哪些相关专业或管理单位协调、先后关系和需要反馈的结果。

不强行给“合规／不合规”二选一，不将未查到审批或材料当作从未办理，不冒充发文机关。收件单位、文号、落款不确定时省略，避免留下看似真实的虚构信息。

## 导出

导出前按 [交付前检查](delivery-check.md) 执行delivery-check，核对摘要、正文、比较表、数值条文来源及照片。export自动重查；明确错误阻止生成，警告及人工核对清单需宿主处理或说明尚待核实，不能当作程序审核结论。

export 请求增加 kind：field_advice／inspection_brief／department_reply。原 kind=consultation（默认）仍导出完整咨询。

专项导出要求最新意见中已有对应 deliverables，且没有在新用户补充后过时；否则先更新分析。每种专项导出各有 Markdown 与 JSON，包含该草稿、当前风险和有来源的信息、规范核验范围与判断边界；不自动附带完整原话和历史。用户若需全部记录，另明确选择完整咨询。

用户明确说“导出Word”时加 format=docx；明确要求附照片时才加 include_photos=true。仅生成所选Word，不自动附全历史JSON。普通聊天不导出，不要求长期保存；关键事实未知可在文中保留，旧意见过时则先更新。现场建议、委托要点、回复草稿和完整咨询均支持Word。

完成Word导出后按documents技能渲染并逐页查看，检查中文、表格、照片、页码及分页；当前宿主无法渲染时如实标记未验证。给文件链接并说明为待核对草稿；不要把导出成功称为专业验收。临时咨询结束清理后，用户明确要求的导出文件仍保留。
