# 交付前一致性检查

当用户说“检查这份意见”“交付前检查一下”，或准备导出当前意见时读取本文件。无需让用户填写检查表或再次确认已授权的导出；由宿主完成核对。只检查最新意见及本次所选交付用途，保持默认临时咨询。

## 先运行程序检查

调用 delivery-check(session_id, kind, format, include_photos)。kind与format沿用export，附图要求也须一致。结果分为：

- errors：明确完整性错误，包括没有意见、意见过时、失效规范／案例引用、无效事实引用、照片缺失或变化、所选交付内容缺失等。修正并重新分析或回源后再导出，不把旧意见当当前意见。
- warnings：需要核对的文字线索，带字段位置和摘录。如数值及单位、标准号、条号未直接匹配当前已知文字事实或有效审阅；正文明确选用了比较表中证据不足或当前不支持的方向；照片尚无实际看图记录。警告不是自动判定错误，也不会自动修正文意。
- manual_checks：程序不能覆盖的语义核对和排版核对。status中包含manual_review_required，不能称为“全文审核通过”或“工程结论正确”。

未发现数值警告，只说明文字直接匹配，不能证明对象、单位转换、来源版本或工程含义正确。程序不会联网查新，不会推测实测值，也不自动判断所有否定、条件、例外或隐含矛盾。

检查逻辑不改写有效咨询；但与所有 CLI 请求一样，分派前仍运行既定过期临时状态清理。不要将“只读检查”解释成整次调用不会删除任何过期记录。

## 宿主完成有内容的核对

1. 对照当前用户原话、事实、未知与纠正，检查摘要、完整分析、所选专项正文和比较表是否表达同一判断。特别检查“待查”是否在另一段变成“已确认”，一个方向的前提或限制是否在别处被删掉；不能只看程序是否返回错误。
2. 逐项看warning的实际位置。数值应确认来源对象、时间、单位和是否仅为示例；条文须核对规范名、版本、原文和适用条件。缺失依据时删除无依据数值／断言，或在对应段明确尚未核实及影响，不从模型记忆补造。用户陈述、报告记载及图片观察不能彼此冒充。
3. 比较表与结论有冲突时修改相关段落并用answer更新整个当前意见，避免仅修改导出的文件造成记录与文件不同。确有两个不同场景的数值或方向，要写清对象及成立条件。
4. 照片实际查看后才记录观察；核对图中区域、图注、拍摄信息和观察限制，不能把未知拍摄时间当本次现场。Word嵌图的字节及图注由程序在临时文件中检查，排版仍须documents技能渲染和逐页查看。

核对后有实质修改则重新answer，再运行delivery-check。无需为交付额外创建长期记录。没有足够证据时可以交付条件化草稿，但必须在正文保留影响判断的缺口，并在回复中说明尚待核查事项。警告有合理原因时说明原因，不为了“清零”而删掉必要边界或伪造事实。

## 导出与历史追溯

export在生成文件前自动重新检查，errors阻止当前交付，不创建或覆盖目标文件；warnings和manual_checks随返回结果提供给宿主，宿主须处理或明确说明仍待核对，不能隐瞒。检查不会自动另生成Word、Markdown或长期归档。

可把delivery-check的content_sha256传为export.expected_check_sha256，绑定内容、来源状态、所选格式及附图范围。其间有变化会拒绝导出并要求重查。导出期间锁定本咨询，避免另一轮更新混入；外部源文件仍须按实际核验时点说明，程序不证明其持续不变。

只有用户明确要求历史记录追溯时才export(history_only=true)，仅完整Markdown／JSON；文件名和正文明确标注“不作为当前意见交付”。不能用历史导出绕过当前Word或专项意见检查，不能自行把用户要求的正式交付改成历史文件。

普通完整咨询的 JSON 仍含原话与历史，Markdown／Word 可能含续办摘要及前次意见；history_only 的区别是历史用途及当前意见有效性要求，不是是否包含历史的开关。专项交付只输出所选用途，分享前仍须核对资料权限。

交付回复说明完成哪些自动检查、宿主核对范围及仍未验证的内容。不声称专业审核、现场验收或自动发现所有矛盾；不主动增加保存／恢复或用户审批步骤。
